Usage guide / Amazon Japan launch system

从选品到复盘，这套流程怎么跑

以一个 SKU、一次 launch 为主线：从证据采集与成本核验，到人工上架、广告计划与每周复盘。下面给出 Agent 的具体输入、命令和预期输出；所有示例按当前脚本与审批契约编写。

最小可执行闭环
13Gate：G0–G12；G12 按完整周循环
14skills：覆盖研究、供应链、Seller Central、FBA 和经营复盘
3Gate 结果：Pass、Needs Proof、Blocked
1总控：amazon-jp-sop-orchestrator 维护状态机和交接包

当前执行逻辑

每次推进都绑定 launch、SKU、Gate 审批记录和文件 SHA-256。计划生成后由运营执行，下一周回收真实数据。

图示对应当前代码。G12 的 gate_decision 表示复盘是否完成，decision 表示经营动作；两者独立。

四条运行规则

只要遵守这四条，流程就不会变成散乱的“分析报告堆”。每个阶段都能被追踪、复用和复盘。

ID

一品一条主线

从第一张表开始保留 candidate_id，成 SKU 后继续补 sku、parent_asin、launch_id。

Gate

没有门禁不推进

使用 record_gate.py 顺序记录审批。Seller / FBA / Ads / Review 必须传入 workspace 与 launch_id；只有旧 pass CSV 无法推进。

Proof

证据先于结论

G6 重算成本并验证八项控制；本地证据及其摘要纳入审批快照。下游会检查文件是否改变，人工利润字段不能覆盖已批准成本。

Loop

投放数据回流

G12 使用完整七天的五类报表。经营结论为 scale / optimize / watch / pause / needs_proof；下一周继续 G12，重复审批不增加记录。

阶段执行表

把它当成项目看板：每一行完成后，把产物放进对应 launch workspace，再让总控更新状态。

Skills 解决的问题

这 14 个 skills 不是独立报告模板，而是一组可串联的岗位能力。每个 skill 负责一个明确问题，并把产出交给下一阶段。

总控

amazon-jp-sop-orchestrator

解决流程散、文件乱、阶段无法追踪的问题。

用法：
先调用它创建 launch workspace、状态机、Gate 和交接包。
产出：
candidate_id、sku、artifact contract、实时数据与周度复盘入口。
实时

amazon-jp-live-data-sync

解决运营数据滞后、报表字段分散、广告和库存无法一起复盘的问题。

用法：
导入 Business Report、Search Term、库存、退货和评论导出。
产出：
live_data/*.normalized.csv、数据质量说明和告警输入。
数据

amazon-data-ingestor

解决 POE、SQP、竞品、供应商报价、广告报表字段不统一的问题。

用法：
把原始 CSV 或粘贴表格先交给它清洗。
产出：
normalized/*.csv，保留证据字段和可关联 ID。
评分

amazon-opportunity-scorer

解决“哪个品值得继续验证”的排序问题。

用法：
输入清洗后的需求、增长、竞争、价格和风险数据。
产出：
Top N 机会、A/B/C/Reject、评分依据和淘汰理由。
风控

amazon-risk-auditor

解决早期选品忽略 IP、合规、FBA 限制、品牌垄断和季节性的风险。

用法：
在推荐候选品前先做风险筛查。
产出：
pass、needs_proof、blocked_pending 和风险证据。
报告

amazon-radar-report

解决机会清单不能转成行动计划的问题。

用法：
在评分和风险筛查后生成周报或月报。
产出：
机会雷达、差异化方向、风险摘要和 7 日验证计划。
供应链

amazon-jp-sourcing-qc-planner

解决供应商、样品、包装和 QC 没有形成可验收证据的问题。

用法：
输入供应商报价和差评痛点，生成样品评估和验货标准。
产出：
supplier_scorecard.csv、qc_checklist.csv、sample review。
硬门禁

amazon-jp-launch-gate

解决 Listing、FBA、广告上线前缺少 SKU 级放行判断的问题。

用法：
在上架前检查类目、JAN/GTIN、IP、标签认证、进口/FBA、毛利和 claim proof。
产出：
pass、needs_proof 或 blocked 的 launch gate report。
产品

amazon-review-miner

解决差评只被总结、没有转成产品改进和 QC 要求的问题。

用法：
输入竞品评论，聚类 1-3 星痛点和可修复缺陷。
产出：
product_requirements.csv、供应商要求、A+ 反驳点和 claim caution。
内容

amazon-jp-listing-aplus-designer

解决日本站 Listing、A+、图片 brief、关键词主表分散产出的问题。

用法：
在 G6 审批通过后，生成日文标题、五点、描述、A+ 模块和图片说明。
产出：
Listing package、A+ module map、amazon_keyword_master.csv。
后台

amazon-jp-seller-central-ops

解决 Listing 包到 Seller Central 实操之间缺少字段、flat file 和人工证明的问题。

用法：
在 Listing/A+ 完成后生成后台上传清单和操作日志。
产出：
seller_central.checklist.csv、seller_central.ops_log.csv。
FBA

amazon-jp-fba-shipment-planner

解决首批备货、标签、箱规、入仓和补货风险靠人工经验的问题。

用法：
输入库存、日销、包规、生产和运输周期，计算发货与补货动作。
产出：
fba.shipment_plan.csv、补货告警和执行 checklist。
广告

amazon-ads-planner

解决广告结构、预算、CPC、否词和复盘规则没有统一口径的问题。

用法：
输入 SKU 经济模型、关键词主表、竞品 ASIN 和搜索词报告。

campaigns.csv、negatives.csv、30 天优化计划和搜索词回流动作。
复盘

amazon-jp-performance-reviewer

解决上线后只看广告、不联动库存、利润、评论和退货的问题。

用法：
按 7/14/30 天或周度导入实时数据，输出经营决策。
产出：
performance.actions.csv、告警、scale / optimize / watch / pause / needs_proof。

Agent usage：输入 → 操作 → 预期输出

以收纳盒 SKU A / launch L1 演示完整交接。命令块可展开查看。

运行准备：Python 3.11+；完整保留 skills 同级目录。工作区是本地审批信任边界，需由团队管理写权限。示例中的 reviewer / operator 代表真实责任人，填写姓名并不替代实际审阅。已有旧工作区若缺少 approvals 快照，需要重新建立审计 launch；不能直接复用旧 pass 文件。

01 / 创建工作区与身份

示例商品：收纳盒；SKU=A；launch_id=L1。命令从本仓库根目录执行。

AGENT INPUT
使用 $amazon-jp-sop-orchestrator，为 SKU A、launch_id L1 在 launches/L1 创建工作区。先检查现有状态，列出 G0–G12 输入缺口；没有证据的门禁标为 needs_proof。

输入：产品信息、负责人，以及可用的数据目录。创建目录不会自动通过任何门禁。

查看对应命令 / 文件内容
python3 skills/amazon-jp-sop-orchestrator/scripts/create_launch_workspace.py --output-dir launches/L1
EXPECTED OUTPUT
launches/L1/ 下生成各阶段目录与 CSV 模板
workflow_state.json：launches 为空，尚无审批
下一步：采集 G0 数据并记录第一次门禁决定

02 / 按顺序完成 G0–G5

每个阶段先形成产物，再由明确的 owner / approver 审阅。不得批量伪造六个 pass。

AGENT INPUT
使用总控依次执行 G0 数据同步、G1 标准化、G2 机会评分、G3 风险审查、G4 供应商和样品 QC、G5 商业验证。输出每阶段产物与证据缺口；实际审批通过后再 record_gate。

输入：原始导出、供应商报价、样品验收、趋势资料；每个 CSV 保留 SKU。样品缺失或失败不能放行。

查看对应命令 / 文件内容
# G0 示例，前提：decision CSV 已由审批人确认
# g0.decision.csv 内容：
launch_id,sku,gate,decision
L1,A,G0,pass

python3 skills/amazon-jp-sop-orchestrator/scripts/record_gate.py \
  --workspace launches/L1 --launch-id L1 --sku A --gate G0 \
  --decision pass --owner operator --approver reviewer \
  --decision-file launches/L1/analysis/g0.decision.csv \
  --evidence-file launches/L1/live_data/report_manifest.csv
# G1–G5 分别使用本阶段的真实决定和证据，按序记录。
EXPECTED OUTPUT
产物：normalized/、机会评分、risk audit、supplier_scorecard、QC 证据与 validation 包
全部顺序审批完成后：current_gate=G6
缺口：needs_proof + 原因 + 负责人；停留在当前 Gate

03 / G6：重算成本，绑定证据

前提：current_gate=G6。以下数值是演示数据，真实运行须替换为可核验报价和凭证。

AGENT INPUT
使用 $amazon-jp-launch-gate 检查 launches/L1/launch_gate 的 evidence_matrix.csv 和 landed_cost_model.csv。输出逐项缺口及重算利润；通过并获 reviewer 审批后记录 G6。

成本输入：售价 1000，货价 400，国际运费 50，税费 50，FBA 50，佣金 50（日元/件），其余成本留空表示 0。证据矩阵必须有八个 control_ref；每行有 owner/source/date 和非空本地凭证。仅标签认证与 claims 允许有依据的 not_applicable。

查看对应命令 / 文件内容
python3 skills/amazon-jp-launch-gate/scripts/evaluate_launch_gate.py \
  --evidence launches/L1/launch_gate/evidence_matrix.csv \
  --costs launches/L1/launch_gate/landed_cost_model.csv \
  --output-prefix launches/L1/launch_gate/launch_gate

python3 skills/amazon-jp-sop-orchestrator/scripts/record_gate.py \
  --workspace launches/L1 --launch-id L1 --sku A --gate G6 \
  --decision pass --owner operator --approver reviewer \
  --decision-file launches/L1/launch_gate/launch_gate.decision.csv \
  --evidence-file launches/L1/launch_gate/evidence_matrix.csv \
  --evidence-file launches/L1/launch_gate/landed_cost_model.csv
EXPECTED OUTPUT
重算：总成本=600；利润=400；毛利/盈亏平衡 ACOS=40%
所有控制有效：launch_gate.decision.csv 的 decision=pass
审批后：current_gate=G7；保存决定、成本、证据矩阵及引用凭证的摘要
缺证明不会通过；单独一份 pass CSV 不能替代审批快照。

04 / G7–G9：内容评审与后台执行

先分别审批 G7 产品要求和 G8 Listing，再进入 G9。G8 需附 listing.csv 与 amazon_keyword_master.csv，之后只消费登记的文件。脚本生成检查清单，运营人员完成后台动作。

AGENT INPUT
使用 $amazon-review-miner 和 $amazon-jp-listing-aplus-designer 形成 SKU A 的产品要求、日文 Listing、claim ledger 和关键词表。G7/G8 审批后，使用 $amazon-jp-seller-central-ops 检查后台就绪度，列出待操作项。

输入：listing.csv 的身份、标题、五点、媒体、价格、配送和合规字段；已批准的 G6 证据；ops_proof.csv 含 sku,field,evidence_file,owner,status=done。每个操作字段应有独立有效凭证。

查看对应命令 / 文件内容
python3 skills/amazon-jp-seller-central-ops/scripts/build_seller_central_checklist.py \
  --workspace launches/L1 --launch-id L1 \
  --listing launches/L1/listing/listing.csv \
  --evidence launches/L1/launch_gate/evidence_matrix.csv \
  --gate-decision launches/L1/launch_gate/launch_gate.decision.csv \
  --ops-proof launches/L1/seller_central/ops_proof.csv \
  --output-prefix launches/L1/seller_central/seller_central
# G9 记录该 decision.csv，并附 listing、checklist 与 ops_proof.csv。
EXPECTED OUTPUT
无操作证明：seller_central.decision.csv = needs_proof，即使字段完整
字段和所有操作凭证均有效：decision=pass；审批 G9 后 current_gate=G10
有效 CLAIMS-JP-01 not_applicable 沿用 G6 规则，不会再次误报缺证据。

05 / G10：生成 FBA 计划并确认凭证

前提：current_gate=G10，G6/G9 审批快照有效。

AGENT INPUT
使用 $amazon-jp-fba-shipment-planner，根据 SKU A 的库存、箱规和日销估计规划发货，检查 FNSKU、箱标、box content、shipment plan 四项凭证，输出缺口。

输入：inventory.csv、package_specs.csv、daily_sales.csv、shipment_proof.csv。首发使用 launch_phase=prelaunch；上线后的库存不足以覆盖交期会阻塞。四项凭证路径必须独立、有效。

查看对应命令 / 文件内容
python3 skills/amazon-jp-fba-shipment-planner/scripts/plan_fba_shipment.py \
  --workspace launches/L1 --launch-id L1 \
  --inventory launches/L1/fba/inventory.csv \
  --package-specs launches/L1/fba/package_specs.csv \
  --daily-sales launches/L1/fba/daily_sales.csv \
  --shipment-proof launches/L1/fba/shipment_proof.csv \
  --gate-decision launches/L1/launch_gate/launch_gate.decision.csv \
  --seller-decision launches/L1/seller_central/seller_central.decision.csv \
  --output-prefix launches/L1/fba/fba
# FBA 的 status 不是 gate decision；经人工审阅另建 G10 pass 行，附该计划。
EXPECTED OUTPUT
fba.shipment_plan.csv：每个 SKU 的建议发货量、覆盖天数、status
缺少凭证：needs_proof；有效首发计划可 pass
人工审核 G10 决定，附 shipment_plan 和所有源输入；审批后 current_gate=G11。

06 / G11：生成受成本约束的广告计划

前提：current_gate=G11。G6、G9 决定与 G10 发货计划都须是本次 launch 登记的文件。

AGENT INPUT
使用 $amazon-ads-planner，为 SKU A 生成日预算 3000 日元、目标 ACOS 25% 的广告计划。只使用已批准 G6 成本；输出 campaigns、targets、negatives 和 economics，并验证预算总额及否词指向。

products.csv：sku=A, asin=ASIN-A, daily_budget_jpy=3000, target_acos_pct=25。关键词行：sku=A, keyword=収納ボックス, relevance=high, conversion_rate_pct=10；另有 risk=blocked 的关键词会进入 Auto/Broad 否词。ASIN-A 是占位符，真实执行须换成真实 ASIN。

查看对应命令 / 文件内容
python3 skills/amazon-ads-planner/scripts/plan_amazon_ads.py \
  --workspace launches/L1 --launch-id L1 \
  --products launches/L1/ads/products.csv \
  --keywords launches/L1/listing/amazon_keyword_master.csv \
  --gate-decision launches/L1/launch_gate/launch_gate.decision.csv \
  --seller-decision launches/L1/seller_central/seller_central.decision.csv \
  --fba-plan launches/L1/fba/fba.shipment_plan.csv \
  --output-prefix launches/L1/ads/ads
# 人工审阅 G11 pass 行；record_gate 附 ads.economics.csv、campaigns、targets、关键词输入。
# 审批后 current_gate=G12；实际投放仍由运营执行并保留记录。
EXPECTED OUTPUT
ads.economics.csv：售价 1000、利润 400、盈亏线 40%、目标 25%
无竞品行时：Auto=840、Broad=660、Exact=930；总计 2430≤3000，未建产品定向的 570 不花出
否词只指向实际生成的 discovery campaign；类型为 negative exact / negative phrase
将目标改为 90%：报错；复用旧 launch 的 pass 或修改成本：拒绝生成。

07 / G12：导入完整周报，计算真实指标

每个 SKU 的交付物包

一个 SKU 能不能被团队接手，取决于这些文件是否齐全。缺一个，后续就会靠口头记忆，复盘也会断。

研究包

normalized/*.csv、opportunities.csv、竞品 ASIN、关键词种子、风险审计和 radar shortlist。

上市包

执行包

增长包

amazon_keyword_master.csv、广告 campaign 文件、否词、搜索词反馈、周度指标、告警和下一轮动作。

下一步判断

每次复盘只做三类决策，避免会议变成泛泛讨论。

Pass

证据齐、毛利达标、风险可控。进入下一阶段，更新状态机，并保留当前版本产物。

Needs Proof

方向可继续，但必须补证据。给负责人、截止时间和所需文件，不允许直接进入广告或 FBA。

Blocked

类目、IP、合规、毛利或执行条件不可接受。归档原因，可作为反例沉淀到选品规则。
